**Phase 9 (Multi-LLM) is implemented, tested, and live-verified against a real local LLM**, per `docs/design/multi-llm.md` (accepted 2026-09-13, implemented 2026-09-13):

- `athena.llm.provider` — a `Protocol`-based adapter (`LLMProvider`) with four implementations (`OpenAIProvider`/`AnthropicProvider`/`GoogleProvider`/`OllamaProvider`), each wrapping exactly one official SDK's genuinely-async client. **`litellm` was re-evaluated and rejected again, more strongly than at ADR-0003's original acceptance**: directly re-checked against GitHub's advisory database for `BerriAI/litellm` and found the situation has gotten worse, not better, since ADR-0003 — a 2026-03-25 supply-chain compromise (GHSA-5mg7-485q-xm76, malicious PyPI releases with credential-harvesting malware, would have affected any installation regardless of usage pattern) plus a sustained run of critical proxy CVEs through the year (including an actively-exploited pre-auth SQL injection, CVE-2026-42208). Every call shape in the adapter (`AsyncOpenAI.responses.create`, `AsyncAnthropic.messages.create`, `google.genai`'s `.aio.models.generate_content`, `ollama.AsyncClient.chat`) was verified directly via `inspect.signature()` against the actually-installed packages, not copied from documentation.
- Every provider call is wrapped in `asyncio.wait_for(..., timeout=...)` uniformly at the adapter layer (never relying on each SDK's own inconsistently-shaped native timeout parameter — Ollama's `chat()` exposes none at the per-call level at all) — confirmed all four SDKs' async clients are genuinely async (httpx-based), so no `asyncio.to_thread` wrapping is needed the way Phase 6's `run_doctor()` fix required (that bug was an internal *synchronous* `asyncio.run()` call, not a blocking network call in general).
- `athena.llm.summarize.summarize_text` — the single entry point both `note_summarize` (MCP) and `athena llm summarize` (CLI) call: enforces the opt-in gate (`ATHENA_LLM_ENABLED`, default **off**, resolving ADR-0007's standing open question per `SECURITY_MODEL.md`'s own recommendation), resolves the configured provider, enforces a daily call ceiling (`ATHENA_LLM_MAX_CALLS_PER_DAY`, default 50 — the "simple cost-ceiling config value" `SECURITY_MODEL.md` asked for, interpreted as a call-count ceiling rather than a dollar-tracker) checked *before* any provider call via the existing `events` table (no new schema — the third phase in a row to add a new audit event type this way), and records an `llm.summarize_completed` audit event afterward — **verified to never include prompt or response content**, closing the Repudiation gap `SECURITY_MODEL.md` flagged for LLM-calling read paths.
- **A real bug found and fixed during testing**: `config.ollama_base_url` always has a truthy default (`http://localhost:11434`), unlike the other three providers' `None`-unless-set API key fields — naively treating "the field is set" as "configured" would make Ollama look configured in *every* environment, including ones with no local Ollama server at all, surfacing as a confusing connection-refused error instead of a clean "not configured" message. Fixed exactly as the design doc's own §2.3 had already anticipated: an explicitly-overridden `ATHENA_OLLAMA_BASE_URL` is trusted outright; a still-default URL counts as configured only if actually reachable right now (checked live via a real HTTP call, never cached).
- `note_summarize` MCP tool — read-only, `open_world_hint=true` per ADR-0007's own classification; frames its returned summary with the same "data to read, never an instruction to follow" convention `note_read`/`vault_search` already use, extended to name that this is *AI-generated and not independently verified* — the provider-response-trust concern `SECURITY_MODEL.md` flagged, addressed with the same defense-in-depth client-side framing already relied on elsewhere. CLI: `athena llm summarize PATH`.
- **Live end-to-end verification against a real local LLM, not just mocks**: pulled a small real Ollama model (`qwen2.5:0.5b`) into this environment's already-running local Ollama server (previously found running two 35B-parameter models used for other purposes, both far too slow on this CPU-only machine for a practical live check) and ran a real summarization through both the CLI and a real in-memory MCP `ClientSession` — both produced a real, coherent summary of a real note's content, with the correct "AI-generated summary" framing on the MCP path. **Phase 8 (Git Automation) recap** — implemented and live-verified 2026-09-12, **committed and pushed as `64bc1c8`** on 2026-09-13 (after fixing a one-character typo in the `origin` remote URL — `ATHENA_AI_GRAIN` instead of `ATHENA_AI_BRAIN` — that had been silently blocking pushes since a prior session), per `docs/design/git-automation.md`:

- `athena.git.wrapper` — the one subprocess primitive every Git operation goes through (`run_git`), implementing ADR-0005's decision in full: `asyncio.create_subprocess_exec` argv-only, never `shell=True`, `GIT_TERMINAL_PROMPT=0` plus a real process-group-killing timeout (so a `push` can never hang on a credential prompt), and a hand-written exit-code/stderr(+stdout) failure taxonomy (`GitFailureKind`: nothing-to-commit, merge-conflict, non-fast-forward, auth-failure, network-failure, not-a-repository, timeout, unknown). A real, empirically-verified `--end-of-options` placement gotcha (it must sit immediately before the pathspec/ref list, never at the front of the whole argv — placing it earlier makes git swallow a real flag like `-b` as a literal pathspec) is documented and encoded in a small `with_end_of_options` helper every call site uses.
- `athena.git.read`/`athena.git.write` — status/log/path-history/ahead-behind (read-only) and commit/push (the only two mutating operations this module can perform — **no function anywhere can force-push, hard-reset, or rewrite history; this is an API-level guarantee, not just an unexposed MCP capability**). `commit_paths` stages and commits *exactly* the given paths, never `git add -A`, so an auto-commit never sweeps in unrelated dirty state. `push` always passes `--set-upstream` — a real finding during implementation: `git push --set-upstream <remote>` (relying on the current branch by omission) fails with "no upstream branch" even against a brand-new remote; `--set-upstream` only works combined with an *explicit* branch name (read via `git rev-parse --abbrev-ref HEAD`, never caller-supplied), closing what would otherwise have been an undocumented one-time-manual-push prerequisite for a fresh vault remote.
- **A second real, empirically-verified git quirk**: `git commit` failing with "nothing to commit" prints that message to **stdout** with an **empty stderr** — the opposite channel from every other failure case here (auth/network/conflict are all on stderr). `classify_git_failure` checks stdout specifically (and only) for this one marker after finding it misclassified as `UNKNOWN` in a real test run.
- `auto_commit_mutation` — the shared, best-effort helper wired into all 7 of this project's mutating MCP tools (`note_create`, `note_update` both modes, `note_link`, `note_move`, `note_delete`, `note_merge`, `research_commit`'s write step) as their final step, per `docs/GIT_WORKFLOW.md`'s already-written auto-commit policy. Never raises — an auto-commit failure can never make the triggering tool call appear to fail — and no-ops cleanly (logged) when the vault isn't a Git repository yet or when `ATHENA_GIT_AUTO_COMMIT=false` (auto-commit itself defaults **on**, per `docs/GIT_WORKFLOW.md`: local-only and non-destructive, safe to default on). Each commit's message names the exact triggering operation and path (e.g. `note_update:patch: Project Ideas.md`) and is recorded as a `git.commit_completed` event — the "structured provenance field" `docs/SECURITY_MODEL.md`'s action item 2 asked for around auto-triggered commits.
- `athena.mcp_server.git_tools` — `git_status`, `git_log`, `note_history` (read-only) and `git_commit` (standalone, mutating, non-destructive, stages+commits *everything* dirty — the one deliberate exception to the narrow-scoping above, since a standalone call has no single triggering mutation to scope to). Not MRTR-gated (append-only, least-destructive category ADR-0007 defines), but every commit is logged. `git_commit`'s MCP default is `dry_run=False` — the opposite of `research_commit`'s default — a deliberate, tested distinction (append-only vs. a real vault write), not an inconsistency.
- A periodic, off-by-default, bounded-retry (`retries=3, retry_delay=30, retry_backoff=2`) `git_push_task` in `athena.worker`, plus `athena doctor`'s new `vault_git_repo` check (warn, not fail — ATHENA AI-BRAIN deliberately never auto-`git init`s a vault; that would be a presumptuous side effect on a user's personal directory) and `vault_status`'s new `git_ahead_by`/`git_last_commit` fields (always live-queried, never cached).
- CLI: `athena git status|log|commit|push`, each with `commit`/`push` requiring an explicit `--commit`/`--push` flag (mirroring `research commit`'s existing pattern, since the CLI has no elicitation fallback).
- **A genuine, previously-flagged gap closed**: ADR-0005 required a `.pre-commit-config.yaml` + gitleaks setup for *this software repository's own* commit hygiene as part of Phase 1 — checked directly and confirmed it was never actually done. Closed this session: `.pre-commit-config.yaml` (gitleaks `v8.30.1`, pinned) + a narrowly-scoped `.gitleaks.toml` path-allowlist for three test files with intentionally secret-shaped fixtures. **Verified for real, not just plausible-looking**: downloaded and ran the pinned gitleaks binary directly against this repo's tracked history (zero false positives, and the allowlist correctly suppresses a planted test private key that gitleaks' default ruleset does flag), then installed `pre-commit` for real and ran the actual hook end-to-end — confirmed it passes cleanly on this repo and genuinely blocks a planted realistic-looking AWS secret (while correctly ignoring the `EXAMPLE`-suffixed placeholder keys this project's own tests already use).
- **Live end-to-end verification, independently re-run, not just trusted from the building agents**: a real scratch vault + real local bare Git remote — `note_create`/`note_update` via a real in-memory MCP `ClientSession` both auto-committed for real (`git_status` reported clean immediately after, `note_history`/`git_log` showed both structured commit messages); `athena git commit`/`athena git push` (CLI) correctly previewed by default and only wrote/pushed with the explicit flag, producing a real commit and a real push to the bare remote (`ahead 0, behind 0` afterward); `athena doctor` showed `vault_git_repo: ok`; `vault_status` surfaced the new git fields correctly (`Git commits ahead of upstream: 0`, `Git last commit: <sha> <message>`).

**Phase 7 (Research & Ingestion) recap** — implemented and live-verified 2026-09-10, **committed and pushed as `9b914dc`** on 2026-09-12, per `docs/design/research-ingestion.md`:

- `athena.research.fetch` — the SSRF-safe fetcher (`fetch_url`), the first code in this project's history that fetches a model/user-supplied URL. Implements `docs/SECURITY_MODEL.md` TB-4's standing, Phase-0-mandated design requirement in full: scheme allowlist (http/https only), DNS resolution against **every** A/AAAA record (not just the first) with rejection of private/loopback/link-local/reserved/multicast/unspecified addresses including IPv4-mapped-IPv6 encodings, a custom `httpx.HTTPTransport` subclass that **pins the TCP connection to the validated IP** (not the hostname) while preserving TLS SNI/cert validation against the real hostname via the `sni_hostname` extension — closing the DNS-rebinding TOCTOU gap a naive validate-then-hand-off-the-hostname implementation would leave open — plus manual, re-validated redirect walking (capped at 5 hops, never `follow_redirects=True`), a content-type allowlist, and a streamed, hard-capped (10 MiB) body read.
- `athena.research.extract` — a thin `trafilatura` 2.2.0 wrapper (`extract_article`), operating only on already-fetched HTML (never `trafilatura.fetch_url()`, which would open a second, unaudited network-egress path). Empirically found and documented: `extract()` with `with_metadata=True` embeds a YAML front-matter block ahead of the Markdown body that would need re-parsing, so this module calls `extract()` (`with_metadata=False`) for the body and `extract_metadata()` separately for title/author/date — cleaner and more reliable, verified against real fixtures. `lxml>=6.1.3` pinned past CVE-2026-41066 (XXE, CVSS 7.5), found during research.
- `athena.research.workflow` — `run_research` (the Huey task body: fetches/extracts each URL independently, one bad URL never aborting the batch) and `commit_draft` (reads a job's draft back and, only when `dry_run=False`, writes it into the vault — reusing `athena.vault.ingest`'s exact write-then-scan-then-redact secret-scanning ordering, closing part of the "`note_create`/`note_update` aren't secret-scanned" gap Phase 6 flagged, and `athena.intelligence.merge`'s crash-safety ordering: filesystem write before any database write).
- Migration `0005_research_drafts.sql` — adds `draft_title`/`draft_body`/`draft_source_urls` to `research_jobs`, closing a real, previously-unnoticed gap between `EVENT_MODEL.md` (which already specified a `draft_handle` on `research.job_completed`) and the schema (which had nowhere to actually store one).
- `athena.mcp_server.research_tools` — `research_start` (task-backed, dispatches `athena.worker.research_task`) and `research_commit` (`dry_run=True` by default; `dry_run=False` requires an MRTR elicitation re-typing the exact topic — directly implementing `SECURITY_MODEL.md` TB-2's standing recommendation that a model alone can't push a real commit, mirroring `note_delete`/`note_merge`'s "accept is necessary but not sufficient" gate). Built directly, not delegated, per this project's practice for a phase's highest-risk code.
- `athena.worker.research_task` — unlike `duplicates_scan_task`/`reindex_task`, this task *does* touch `research_jobs` itself (the draft is per-job state only it computes). Since its own `job_id` isn't known at dispatch time (mirroring `duplicates_scan`/`reindex_start`'s existing insert-after-dispatch order), it uses Huey's `context=True` to receive its own `Task` instance and look itself up by `huey_task_id` — raising (letting Huey's `retries=3, retry_delay=10` handle it) if the dispatcher's row hasn't landed yet.
- CLI: `athena research start --url URL [--url URL ...] --topic "..."` / `athena research commit JOB_ID [--commit] [--target-path PATH]` (an explicit `--commit` flag, not merely omitting `--dry-run`, since the CLI has no elicitation mechanism).

**Phase 5 (Knowledge Intelligence) recap**, per `docs/design/knowledge-intelligence.md` (accepted 2026-09-04, implemented 2026-09-04):

- `athena.intelligence.duplicates` — four-signal duplicate detection (exact `content_hash`, lexical `MinHash-LSH` via `datasketch` 2.0.0 pinned to `scheme="affine32"`, semantic cosine similarity via a new Qdrant "query by existing point ID" mechanism, and `difflib`-based metadata/filename matching that only ever annotates a pair the other three already found), fused into a `combined_score` and upserted into `duplicate_candidates`. Degrades to three signals if Qdrant is unreachable; a note with no chunks only skips the semantic signal, not the whole scan.
- `athena.intelligence.merge` — the review/merge engine: `list_pending_duplicates`/`resolve_duplicate` (explicit confirm/reject, never automatic — Master Spec §10's "a high similarity score must not automatically imply... interchangeable") and `merge_notes`, reachable only from a `'confirmed'` candidate. Appends the absorbed note's content under a `## Merged from` heading, re-indexes the kept note (best-effort — a re-index failure is logged and does not abort the merge), tombstones and supersedes the absorbed note, and writes a PROV `provenance` row. **Verified live**: DB state after a real merge showed exactly the expected `notes`/`duplicate_candidates`/`provenance` rows, including correct graceful degradation when the post-merge re-index hit an unreachable Qdrant server.
- `athena.intelligence.related` — on-demand "related notes" via the same query-by-point-ID mechanism as the semantic-duplicate signal, at a lower similarity threshold; deliberately not persisted (results go stale the moment content changes).
- `athena.intelligence.lifecycle` — two narrow, explicitly-accepted policy additions to Master Spec §11's still-open lifecycle-transition-rules question: automatic `'draft' → 'active'` promotion the first time a note is successfully indexed, and a stale-sweep policy (`'active'`/`'verified'` → `'stale'` after 180 days untouched, skipping notes already in the duplicate-review queue). Both go exclusively through the existing `transition_status()`, never a direct `notes.status` write.
- `athena.db.repository.provenance` extended with `insert_derivation`/`get_lineage` (walks `provenance`/`provenance_derivations` to answer "what did this note come from/become," entirely from already-existing schema, no new tables).
- A new `athena.db.repository.duplicates` module (`duplicate_candidates`/`note_minhash_signatures` CRUD) and `athena.retrieval.vector_search.find_similar_by_point_id` (confirmed via the Qdrant API reference that `query_points` accepts an existing point ID directly, self-excluded via a `must_not`/`HasIdCondition` filter — no retrieve-then-resubmit round trip, no race against a concurrent re-index).
- CLI: `athena duplicates {scan,list,resolve,merge}`, `athena lifecycle stale-sweep`. Worker: `run_duplicates_scan/list/resolve/merge`, `run_stale_sweep`, plus a new daily `stale_sweep_task` periodic job alongside the existing hourly reconciliation.

## Why no Article-2 design document

CLAUDE.md rule 8 requires "every feature gets a design document before
implementation." Phase 11 isn't a feature — it's a release process
applied to already-implemented, already-tested code. Writing a design
doc for "bump a version number and tag a commit" would be process
theater, not genuine design work. This is a deliberate, reasoned
exception, not a shortcut — documented here explicitly so it doesn't read
as an inconsistency against the project's own stated rules.

## A real finding from doing this for the first time

`pyproject.toml`'s `version` field and `src/athena/__init__.py`'s
`__version__` string are **two separate values, not synced from a single
source** — `athena version`'s CLI output reads the hardcoded
`__version__`, not `importlib.metadata`. Bumping only `pyproject.toml`
would have left the CLI reporting a stale version. Found by directly
grepping for `"0.1.0"` across the repo rather than assuming
`pyproject.toml` was the only place it lived. Fixed both, and updated
`docs/RELEASE_CHECKLIST.md`'s step 5 to name this explicitly so a future
release doesn't repeat the same near-miss.

## A second real finding: this project's first-ever CI run actually failed

Watching CI go green was supposed to be a formality (639/639 had already
passed locally, repeatedly, throughout Phase 10). It wasn't — CI's
`pytest -q` step failed at collection time with 9 `ModuleNotFoundError: No
module named 'tests'` errors (`ruff`/`mypy` both passed cleanly first).

**Root cause**: nine test modules (established in Phase 8, reused since —
`tests/git/{test_read,test_write}.py`, several `tests/mcp_server/*.py`
files, `tests/research/test_workflow.py`, `tests/test_diagnostics.py`) do
`from tests.git.conftest import init_repo`/`commit_all` — an absolute
dotted import that requires the repo root to be on `sys.path` so `tests`
resolves as a package. Locally, every session's own verification ran via
`python -m pytest`, and Python's `-m` invocation implicitly prepends the
current working directory to `sys.path[0]` — silently satisfying this
requirement every single time, in every prior phase's own testing,
without anyone (agent or human) ever invoking bare `pytest` locally to
notice the gap. CI's own `pytest -q` step (no `-m python`) gets no such
implicit insertion, and `pyproject.toml`'s `[tool.pytest.ini_options].
pythonpath` only listed `["src"]` — enough for `import athena`, not
enough for `import tests`.

**This is a real, previously-invisible fragility that had existed since
Phase 8** (whenever the first `from tests.X.conftest import ...` pattern
was introduced) — masked for four phases (8, 9, 10, and the start of 11)
purely because nothing had ever run this project's test suite any other
way until real CI did, for the first time, this session.

**Fix**: added `"."` to `pythonpath` in `pyproject.toml`'s
`[tool.pytest.ini_options]` (`["src"]` → `["src", "."]`) — the repo root
is now on `sys.path` for every invocation style, not just the one every
session happened to use. Verified by reproducing the failure locally
first with the *exact* bare `pytest -q` invocation CI uses (confirmed it
failed identically), then confirming the fix resolves it under that same
bare invocation — not just re-confirming via `python -m pytest`, which
would have silently passed either way and proven nothing.

## A third real finding: a genuine Python-version-dependent crash in the vault safety boundary itself

Pushing the fix above (commit `182bfa7`) triggered CI again. Ruff and
mypy passed again; pytest failed a second time, differently — 2 real test
failures (not a collection error), both `PermissionError` propagating
unhandled out of `athena.safety.paths._check_no_symlinks_in_chain` (P0
security item #1, the core vault path-traversal defense) for a traversal
attempt through `../../../../../../../root/.ssh/id_rsa`.

**Root cause**: `pathlib.Path.is_symlink()`'s stdlib implementation
changed between Python 3.12 and 3.13+. On 3.12 (this project's declared
`requires-python = ">=3.12"` minimum, and CI's pinned version), it calls
`self.lstat()` directly and only swallows a narrow allow-list of
`OSError` subtypes (`ENOENT`/`ENOTDIR`/`EBADF`/`ELOOP`) — `PermissionError`
(`EACCES`) is *not* in that list and propagates. On 3.13+, the
implementation was rewritten to delegate to `os.path.islink()`, which
swallows `OSError` broadly and returns `False`. This dev environment runs
Python 3.14 — confirmed directly (`python3 --version`) — so every one of
this project's prior local "all tests passing" claims, across four
phases, was genuine but exercised the newer, more forgiving behavior the
whole time, without anyone ever running the suite under 3.12 locally to
notice the gap.

**Why this matters more than the `sys.path` finding**: that one was a
test-infrastructure gap. This one is a real crash in production security
code, on the project's own officially-supported Python version, triggered
by exactly the kind of input (a deep `..` traversal into another user's
home directory) this function exists to defend against. An unhandled
`PermissionError` propagating out of a path-safety check is a worse
failure mode than a clean rejection, even though in this specific case no
actual escape occurred — the downstream `resolve(strict=True)`-based
checks a few lines later already handle exactly this class of error
correctly (with an explicit comment: "an inaccessible ancestor ... this
module cannot vouch for the path"), but `_check_no_symlinks_in_chain`,
which runs *before* those checks, had no equivalent handling and crashed
first.

**Fix**: wrapped the `current.is_symlink()` call in `_check_no_symlinks_in_chain`
in `try`/`except OSError`, treating an inaccessible ancestor as "cannot
verify either way" and letting the loop continue — exactly matching the
reasoning the function's own downstream `resolve(strict=True)` calls
already use. This makes the module's actual behavior version-independent
rather than accidentally depending on which Python runs it, instead of
only fixing the CI-visible symptom.

**Verified without a local Python 3.12 interpreter available**
(`which python3.12` found nothing): rather than trust the fix on
reasoning alone, directly simulated 3.12's exact `is_symlink()` behavior
via a monkeypatch (reimplementing the narrow-allow-list version) in a
standalone script first, confirmed the *unfixed* code would crash under
it, then confirmed the fix resolves it. Then added a permanent regression
test using the same monkeypatch technique directly in
`tests/safety/test_paths.py::TestSymlinks::
test_permission_error_on_an_inaccessible_ancestor_does_not_crash`, so this
doesn't silently regress again the next time this environment's Python
version changes. 640/640 tests passing after the fix (639 + 1 new).
Pushed as a small follow-up commit; CI re-ran and passed in full (ruff,
mypy, pytest) on the new commit before tagging proceeded.

## What was deliberately left alone

`docs/ARCHITECTURE.md` was **not** updated, despite several of its own
"Consolidated Open / Deferred Decisions" (§6) having been resolved
organically in later phases without ever formally closing them there
(the Huey `aget_result()` async-bridge validation, `chonkie`'s frontmatter
handling, the provenance schema, the SQLite connection-management
pattern, the FTS5 quiet-window tuning, the `fs.inotify` sysctl
documentation). The document is explicitly self-labeled a "Phase 0
exit-criteria deliverable" — a historical snapshot of the state of
understanding at Phase 0's close, not a living per-phase document.
Retroactively rewriting it wasn't asked for, and silently doing so would
risk quietly redesigning what that document is *for* rather than just
correcting a factual error. Flagged in `NEXT_SESSION.md` as an open
question for a future session to decide explicitly, not acted on here.
